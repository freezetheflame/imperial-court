# 皇帝体验设计（Emperor Experience Design）

> 状态：设计基线 v0.1（2026-08-05）
> 范围：前端交互 + 与后端/prompt 的契约变更。本文件是"皇帝体验"的唯一设计权威，
> 后续实现（人工或 codex）以本文件为准；与 `frontend-throne-spec.md`（场景视觉 v2）冲突时以本文件为准。

---

## 0. 设计哲学：皇帝的感觉 = 权力仪式，不是场景装饰

核心判断：**皇帝体验的差距不在"有没有金銮殿"，而在"皇帝有没有笔、印、时间、回响"。**

已有实现已经把"场景"做完了（金銮殿 CSS 场景、丞相进殿动画、奏折卷轴、政事进度、SSE 实时推送），
但皇帝的决策动作仍是"点按钮"——这是审批系统，不是临朝听政。

皇帝感由 **四个仪式闭环** 构成，缺一不可：

| 闭环 | 含义 | 现状 |
|---|---|---|
| **笔** | 朱批是"写"出来的，不是"点"出来的 | ❌ comment 硬编码为字符串"朱批"（ThroneHall.tsx:49） |
| **印** | 决策要盖章，有重量、有仪式 | ❌ 无玉玺盖章动作 |
| **时间** | 皇帝掌控节奏：想批才上朝，奏章堆着等御览 | ❌ SSE 推着皇帝走（奏折一到就触发动画） |
| **回响** | 朕的一笔，天下响应：准→执行→办结；驳→重办→复奏；革职→空缺→任命 | ❌ 批完即归档，后果不可见 |

**一句话定位**：皇帝体验 = 大臣拟议（票拟）+ 皇帝裁断（朱批盖章）+ 天下响应（起居注因果链），
全部包裹在皇帝自主掌控的朝会节奏里。

## 1. 现状诊断（2026-08-05 代码基线，commit 0bc4eee）

### 1.1 已具备

- 金銮殿主场景（`ThroneHall.tsx`）：匾额、殿柱、丹陛、香炉烛火、奏匣（memorial drawer）、奏折卷轴展开/合拢动画

- 政事进度面板（`CourtProgressPanel.tsx`）：上谕执行百分比 + 子任务清单（3s 轮询）
- 御史台案卷页（`CensoratePage.tsx`）、百官名册页（`PostsPage.tsx`）、拟旨页（`EdictsPage.tsx`）
- SSE 实时推送（`useEventStream`）、React Query 缓存
- 后端：奏折批红 API 已支持 `comment` 字段（`POST /api/memorials/{id}/verdict`）

### 1.2 四个缺口（G1-G4）

| # | 缺口 | 代码证据 | 后果 |
|---|---|---|---|
| G1 | **批红不能写字** | `ThroneHall.tsx:49` `api.verdictMemorial(id, value, "朱批")` — comment 是硬编码字符串；`CensoratePage.tsx:14` 同样 | 皇帝只有 4 个按钮，无自由朱批 |
| G2 | **无票拟** | 奏折数据结构（api-contract.md §2）只有 `content`，无"臣拟"意见 | 皇帝被迫全文阅读、自主判断 → 认知负担=打工感 |
| G3 | **节奏被动** | `ThroneHall.tsx:31-34` 新奏折到达自动触发呈奏动画 | 系统催皇帝，而非皇帝召见臣工 |
| G4 | **后果不可见** | 批红 onSuccess 仅 `invalidateQueries` + 归档，无因果链展示 | 批完就结束，感受不到"朕的一笔，天下响应" |

## 2. 总流程设计：朝会（Court Session）

### 2.1 概念模型

```
┌─────────────────────────────────────────────────────────┐
│  皇帝（用户）— 唯一主动方                                  │
│                                                         │
│  非朝会（日常）：                                         │
│    奏章抵达 → 奏匣红点提示（不打断）→ 皇帝随时可"上朝"      │
│    加急/弹劾直奏 → 角标提示（金红令牌动画，可打断一次）      │
│                                                         │
│  朝会（核心交互）：                                       │
│    上朝 → 待批奏章逐封呈现 → 朱批（写+选）→ 盖章 → 合拢    │
│        → 下一封 / 散朝                                    │
│  散朝总结：今日批 N 封、办结 M 事、待办 X 封               │
└─────────────────────────────────────────────────────────┘
```

### 2.2 朝会状态机

```text
IDLE ──(点击"上朝"/奏匣)──▶ COURT_OPENING ──▶ REVIEWING
                                              │
                    ┌─────────────────────────┤
                    ▼                         ▼
              VERDICT_WRITING           NEXT_MEMORIAL（自动展开下一封）
                    │                         │
                    ▼                         │
              SEAL_STAMPING                  │
                    │                         │
                    ▼                         │
              SCROLL_CLOSING ─────────────────┘
                    │
                    ▼
            ┌─ 还有待批 ─▶ REVIEWING
            │
            └─ 批完/主动散朝 ─▶ COURT_ADJOURNING ─▶ SUMMARY ─▶ IDLE
```

- 状态由前端 `CourtSession` 组件管理，复用现有 CSS 动画关键帧（arriving-scroll / departing-scroll）。
- 朝会期间丞相进殿动画**不再自动触发**（G3 修复），改为奏匣红点 + 可选的"急奏"短提示。

## 3. 设计细则

### P0（🔴 最高优先）：朱批书写 + 玉玺盖章

**目标**：皇帝从"点按钮"变成"写朱批、盖玉玺"。

**交互规格**（奏折卷轴展开后，`status === "submitted"` 时）：

```
┌─ 奏折卷轴（展开）──────────────────────────┐
│  臣工谨奏 · 丞相                              │
│  正文……（横排）                               │
│  ── 票拟（P1）：臣拟：准，理由……              │  ← 墨色淡，P1 加入
│                                              │
│  ── 朱批区 ────────────────────────         │
│  [照准] [知道了] [驳回] [留中] [发回重办]      │  ← 快速短语 chips（点击填入输入框）
│  ┌──────────────────────────────────┐        │
│  │  （自由输入，楷体、朱红 #8b1a1a）   │        │  ← 皇帝亲手写批语
│  └──────────────────────────────────┘        │
│  [盖 章]                                      │  ← 主按钮；无文字时禁用或提示
└──────────────────────────────────────────────┘
```

**盖章动画序列**（约 1.2s，CSS 实现，spec 已有 `.seal` 样式复用）：
1. 朱批文字以"笔迹"渐显（淡入 + 轻微旋转抖动，模拟落笔）
2. 玉玺方印（红色双线方框 + "御览之宝"或"准"）从上方旋转落下，落定后轻微回弹
3. 卷轴合拢 → 丞相谢恩退下（复用 departing 流程）→ 若朝会中则自动展开下一封

**数据流（零后端改动）**：
- `POST /api/memorials/{id}/verdict` body: `{ "verdict": "approved|rejected|held|returned", "comment": "<朱批文字>" }`
- 快速短语 → verdict 映射：照准=approved / 知道了=approved（comment="知道了"）/ 驳回=rejected / 留中=held / 发回重办=returned
- 自由输入必填时，无输入则禁用盖章（或默认"知道了"）
- 已批奏折的朱批文字回显于卷轴（`selected.verdict` 旁，红字楷体）——后端需在详情/列表返回 `comment`，见 §5

**组件**：新增 `VermilionPanel.tsx`（朱批区 + 盖章），改 `ThroneHall.tsx`（接入朝会状态机时替换 verdict-row）。

---

### P1（🟠）：票拟——大臣拟议，皇帝裁断

**目标**：丞相/御史呈报时附"臣拟：____，理由：____"，皇帝扫一眼即可"照准"，把判断负担从皇帝移到臣工——这是制度感的骨架。

**后端/prompt 契约**：
- 丞相复奏 prompt 追加固定输出格式（提示词级，一行规则）：
  ```
  复奏末尾必须输出一行票拟，格式：
  臣拟：<准 | 驳 | 发回重办>，理由：<一句话>
  ```
- 御史台弹劾案已有 `recommendation` 字段（warning/removal），前端已渲染"台议"——此为其奏折版对齐。
- 可选：后端在 `POST /api/memorials` 或读详情时解析票拟存 `recommendation` 字段（结构化），
  否则前端从 `content` 末行正则提取展示即可（v0.1 采用正则方案，零后端改动）。

**前端渲染**：卷轴正文下方、"朱批区"上方，独立一行：`票拟 · 拟准：理由……`，墨色淡、字号略小、与正文区分；供皇帝快速决策。

---

### P2（🟡）：朝会节奏——皇帝掌控时间

**目标**：把"系统推着走"改为"皇帝召见"。

**交互规格**：
1. **日常态**：新奏章到达 → 奏匣数量红点 + 轻微角标动画（不弹丞相、不自动展开）；急奏/弹劾直奏用金红令牌角标（短促一次）
2. **上朝**：点击"上朝"→ 场景淡入朝会态 → 第一封待批奏章展开（复用卷轴动画）
3. **朝会中**：朱批盖章后自动展开下一封；底部显示"第 X/Y 封"
4. **散朝**：点"散朝"或批完最后一封 → 总结面板（今日批 N 封 · 办结 M 事 · 待批 X 封 · 弹劾待决 Y 件）
5. **随时可中止**：合上卷轴即回到日常态，待批保留

**组件**：新增 `CourtSession.tsx`（状态机），改 `ThroneHall.tsx`（接替现有 stage 逻辑）、`ChancellorArrival.tsx`（日常态不再自动触发；朝会中保留"臣工进殿"氛围动画仅在展开时播放一次）。

---

### P3（🟢）：起居注因果链——朕的一笔，天下响应

**目标**：决策后果可视化，形成"准→执行→办结；驳→重办→复奏；革职→空缺→任命"的闭环感受。

**数据源（零后端改动）**：`GET /api/events?kind=...&limit=50`（事件流 = 史册 = 御史台数据源，api-contract.md §5），
按 `edict_id` / `post_id` 聚合。

**UI 规格**（金銮殿侧边抽屉或独立入口"起居注"）：
- 每条上谕一张"因果链"卡片，时间正序：
  ```
  下旨（edict）→ 丞相拟旨（agent_activity）→ 执行岗办理（tool_call）→ 复奏（memorial）
  → 御批（朱批文字 + verdict）→ 办结/发回重办（memorial 状态变化）
  ```
- 违制/弹劾事件插入链中（`violation` / `impeachment`），红色标记
- 支持按岗位过滤（点击名册某官牌 → 看此官全部行为，= 御史查案视角）

**组件**：新增 `ChroniclePanel.tsx`。

## 5. 契约变更（最小化）

**后端现状（已核实，2026-08-05）**：
- `POST /api/memorials/{id}/verdict` 已接收 `comment`，但 `court/memorials.py:103-110` **只把 comment 写入 events 表**（`insert_event("memorial_verdict", ..., {verdict, comment})`），未存入 memorials 行——`storage` schema 无 comment 列。
- 推论：① `GET /api/memorials` 返回的奏折**不含**朱批文字；② events 表（史册）天然保留 verdict+comment，是 P3 起居注的现成数据源；③ 发回丞相的重办 payload 已带 comment（`memorials.py:114-122`）。

**必做（P0 回显）**——二选一：
- **方案 A（推荐，改动最小）**：memorials 表加 `comment TEXT` 列；`verdict()` 的 UPDATE 带上 `comment = ?`；`GET /api/memorials` 返回 comment。约 3 行改动 + 1 次 schema 迁移（SQLite `ALTER TABLE`，demo 库可直删重建）。
- 方案 B（零后端改动）：前端已批奏折的朱批从 events 查询聚合（`GET /api/events?kind=memorial_verdict`）——但列表接口不支持按 memorial_id 过滤，需要前端拉全量过滤，不推荐。

**可选**：奏折结构化 `recommendation` 字段（v0.1 用正则提取票拟，不做）。

**不动**：`/verdict` 语义、SSE 事件类型、上谕/弹劾/官职端点。

## 6. 验收标准

1. `npm run build`（tsc -b && vite build）通过，无未用 import、类型正确
2. 打开首页为金銮殿；新奏章到达**不再自动弹丞相动画**，仅奏匣红点提示
3. 上朝 → 奏章展开 → 可写朱批（快速短语 + 自由输入）→ 盖章动画 → 合拢 → 自动下一封 → 散朝总结
4. 请求体 `comment` 为真实朱批文字（不再是硬编码"朱批"）；已批奏折回显朱批
5. 票拟行显示于正文与朱批区之间
6. 起居注因果链：上谕从下旨到办结完整可查，违制/弹劾红色插入
7. 弹劾裁决同样支持朱批 + comment
8. 响应式不崩；现有功能（拟旨、名册任命、御史台、SSE）不丢

## 8. 反模式对照（设计红线）

以下形态**不代表皇帝体验**，实现时禁止回退：

- ❌ 审批按钮流（点"同意"完事）→ ✅ 写朱批 + 盖章
- ❌ 仪表盘/进度条主导（CFO 视角）→ ✅ 奏章/卷轴叙事主导，进度仅作辅助（CourtProgressPanel 保留但次要）
- ❌ 通知轰炸（消息推送驱动）→ ✅ 奏匣红点 + 皇帝主动上朝
- ❌ 全程只见按钮不见人（无臣工存在感）→ ✅ 票拟署名 + 呈奏人官职 + 革职/任命人事变动可见
